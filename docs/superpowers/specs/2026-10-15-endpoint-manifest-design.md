# Endpoint manifest: static imports for file-based routing

**Date:** 2026-10-15
**Status:** Implemented
**Scope:** `packages/nestjs-endpoints` (router, CLI, docs), test apps, example.
Breaking change for consumers of file-based routing.

## Goal

File-based routing stops discovering endpoint files with `readdir` and loading
them with an `import()` that lives inside the library. Instead, a generated
manifest in the app's own source tree (`src/endpoints.gen.ts`) holds one
`() => import('./…')` per endpoint / router module file. The router walks the
manifest instead of the filesystem, and loads files through those loaders.

## Why

A route set discovered at runtime, and imported from inside `node_modules`, is
invisible to every tool that works from the app's import graph:

- **Vitest** externalizes the installed library, so the library's `import()`
  runs in plain Node: endpoint files skip Vite (no path aliases, no decorator
  metadata, a second copy of every module). Consumers had to add
  `server.deps.inline: ['nestjs-endpoints']`.
- **`node --watch` / `tsx watch`** only watch files already imported, so a new
  endpoint file is not served until a manual restart.
- Each tool needs its own workaround; libraries with the same design (e.g.
  `@fastify/autoload`) end up sniffing for ts-node, tsx, Vitest, Jest, …

With the loaders written in app source, Vite transforms them like any other
app import, and the manifest itself is part of the watched graph.

## Design

### The manifest file

```ts
// Generated by nestjs-endpoints. Do not edit: the app keeps this file in
// sync while it runs in development, and `npx nestjs-endpoints generate`
// rewrites it on demand.
import { registerEndpointManifest } from "nestjs-endpoints";

registerEndpointManifest(import.meta.url, {
  importExtension: "js",
  files: {
    "blog/endpoints/list.endpoint.ts": () => import("./blog/endpoints/list.endpoint.js"),
    "blog/router.module.ts": () => import("./blog/router.module.js"),
  },
});
```

- Keys and specifiers are emitted with `JSON.stringify` (file names carry `$`,
  and may carry quotes). No `eslint-disable` header: ESLint 9 reports an unused
  directive, which `--max-warnings=0` hooks reject.

- Keys: paths relative to the manifest's directory, POSIX separators, source
  extension. Sorted.
- Loaders are **lazy** (`() => import()`), not static imports. That keeps the
  existing contract that endpoint files are evaluated inside the router's
  `moduleAls.run(...)`, where `endpoint()` defers its setup until the router
  knows its root directories and base path. Lazy literal `import()`s are still
  seen by Vite, bundlers and watchers.
- `importExtension`: `'js'` (default; works with tsc, tsx, Vite, swc) or `'ts'`
  (Node's native type stripping, which requires real `.ts` specifiers and
  `allowImportingTsExtensions`). Stored in the file so regeneration preserves it.
- Scope: everything under the manifest's directory matching the endpoint or
  router-module file patterns. Skips `node_modules` and dot-directories, and
  `.d.ts` files. A `.ts` and `.js` file with the same stem collapse to one entry
  (the `.ts` one).

### Registration and lookup

`registerEndpointManifest(url, …)` records the manifest in a process-global
registry, keyed by manifest file; registering the same file again replaces the
entry (Vitest can keep an externalized library loaded while it re-evaluates the
app per test file, and the latest loaders are the live ones). A router resolves its root directories against the registry: each
root must sit inside a registered manifest's directory. The app imports the
manifest once (`import './endpoints.gen.js'` in `app.module.ts`).

`EndpointRouterModule.create()` returns a **lazy** promise: it captures the
callsite and the parent router context synchronously, but does its work only
when awaited — which Nest does while scanning modules, after the app's static
import graph has been evaluated. So it does not matter whether the manifest
import is evaluated before or after the router modules (it often is not: routers
imported by `app.module.ts` evaluate first, and Vite's runner evaluates imports
asynchronously).

A router whose root directories are covered by no manifest throws, naming the
directory and how to fix it — unless it declares explicit `endpoints`, in which
case there is nothing to discover and discovery is skipped.

### Discovery

The existing recursive walk (`findEndpoints`) runs unchanged over a virtual
directory tree built from the manifest instead of `fs.readdirSync`. Ordering is
deterministic (sorted names, depth-first), matching what a sorted `readdir`
gave. Matching a discovered file against the endpoint registry (`settings.
endpoints[].file`, the callsite of `endpoint()`) and against the caller's own
router module compares paths without extensions, since in production the
manifest keys are `.ts` while the running files are `.js`.

### Keeping it current

The app keeps the manifest correct itself; there is no generator process.
Mode is chosen from the environment:

| Condition | Behavior |
| --- | --- |
| `NODE_ENV=production` | Trust the manifest. No scanning. |
| `CI` set (and not production) | Scan the source tree; if the manifest is stale, throw with the diff and the fix. Never write. |
| otherwise (development, tests) | Scan; if stale, rewrite the source manifest and log the diff. In development only (`NODE_ENV` unset or `development`; Vitest sets `test`), then watch the source tree and rewrite on any add / delete / rename. |

- **Stale** means the set of keys differs from a fresh scan (`importExtension`
  only changes through the CLI, and rewrites keep it). Compared as data, not text, so a formatter touching the file never
  causes churn.
- **Locating the source manifest:** when the running manifest is `.ts`/`.mts`
  it is the source. When it is compiled `.js` (e.g. `nest start --watch` runs
  `dist/`), the source is found through its source map (external
  `.js.map` or inline). If none is found, sync is skipped with one warning.
- **Writes** are skipped when the file already holds the same text (a compiled
  app's `dist/` copy can lag a source manifest that is already current, and a
  needless write restarts watchers); otherwise they go to a temp file renamed
  into place (parallel test workers may write at once). A failed write only
  warns.
- **In the current process**, after detecting staleness: only keys present in
  the fresh *source* scan are loadable — not merely files that exist where the
  app runs, since `tsc` leaves a deleted endpoint's `.js` in `dist/` — so deleting an endpoint never crashes boot; new
  files are served after the restart the manifest write triggers under
  `--watch` (the log says so). Without a watcher, restart manually. Under
  `NODE_ENV=test`, added files make that run fail after the rewrite, asking to
  re-run: later test files in the same run would load the new manifest, so
  serving 404s in the first would look like flakiness.
- **Live watching**: `fs.watch(sourceDir, { recursive: true })`, debounced,
  `unref()`ed so it never holds the process open, one per manifest. On any
  change (outside dot-directories, `node_modules` and the manifest itself) it
  rescans and rewrites if the key set changed; a full rescan catches directory
  renames reported as one event. One rescan right after it starts covers
  changes between the startup scan and the watcher going live. Under `node --watch` /
  `tsx watch` the rewrite restarts the app with the new route set.

### CLI

- `nestjs-endpoints init` additionally writes `src/endpoints.gen.ts` (when
  `src/` exists), adds `linguist-generated` to `.gitattributes` and the file to
  `.prettierignore` (only when the project has one), and prints the one import
  line to add to the app module. `init --refresh` (postinstall hooks) stays
  skill-only. Flags: `--dir <dir>`,
  `--import-extension ts|js`.
- `nestjs-endpoints generate [--dir <dir>] [--import-extension ts|js]` writes the
  manifest. Without the flag it preserves the existing file's extension
  setting.

## Non-goals

- **Single-file bundling.** Loaders are bundler-visible, but URL inference still
  derives paths from each `endpoint()` callsite's file, which a bundle
  collapses. Unchanged here.
- **Rewriting user files** (e.g. inserting the import into `app.module.ts`).
- **A fallback to the old library-side `import()`** when the manifest is
  missing or stale. One loading mechanism only.

## Testing a single router

A test may import one router module without the app module. It imports the
manifest too (or lists it in Vitest's `setupFiles`); registration loads no
endpoints, so only that router's subtree is loaded. The missing-manifest error
says so.

## Testing

- Unit: generation (scope, exclusions, ordering, dedupe, extensions), virtual
  discovery, staleness/sync modes, source-map lookup, watcher add/delete.
- E2E: the express test app commits its manifest (fastify's `src/` is a
  mirror). Both apps' Vitest configs force the library to be externalized, as an
  installed copy is — the regression run for the Vitest problem. The app module
  imports the manifest last, proving import order does not matter. A spec loads
  a single router module.
- The example app installs the library from `node_modules`, so its full-app
  test is the real-install proof.
